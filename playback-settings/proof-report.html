Playback settings: proof of work

The app tells Jellyfin what this Mac can handle, and the server sends the file as-is or transcodes it. This page collects evidence from three independent sources: the app's GUI on a clean macOS 13 VM, the app's own log, and the Jellyfin server's /Sessions API polled separately from the host.

BuildDMG built in a clean Tart VM (make vm-dmg) from branch feat/playback-quality
Run onmacOS 13.7.4 (Tart VM ztriton-ventura-proof)
ServerJellyfin 10.11.5 (container on the host)
Media1080p H.264/AAC MP4 · 4K HEVC 10-bit HDR10 MKV with AC-3
Slow network: on a link capped at 4 Mbps, a 12 Mbps movie at Maximum stalls about 7 times in 40 s and plays at roughly 27% of real time. Lowered to 2 Mbps, it plays at 100% with 0 stalls. Details
Verdict: all 10 acceptance criteria of issue #13 are met. The server's own session data shows each change: Transcode at 1280×720 for the saved 720p, then 640×360 or 853×480 after an in-player change, with the saved default unchanged.

Slow network: lowering the bitrate stops the stutter

Experiment: a proxy caps the connection between the Jellyfin server and the player at 4 Mbps, like slow Wi-Fi. A 12 Mbps 1080p H.264 movie (constant bitrate, 90 s) plays through ztriton's own player engine (Player, libmpv), the same code the app uses, for 40 s per setting. A stall is mpv pausing playback to wait for data, which the app shows as "Buffering…". The test is tests/slow_network_e2e.rs; anyone can re-run it with cargo test --release --test slow_network_e2e.

Result, repeated 3 times: at Maximum the 12 Mbps file cannot fit through the 4 Mbps link. Playback stalls about every 5 s and moves at about ¼ speed. Lowering the bitrate to 2 Mbps makes the server transcode to fit, and the movie plays at full speed with zero stalls in every run. Auto measures the slow link and also transcodes, removing nearly all stalling.

Auto has no safety margin. It uses exactly the measured speed (3.3–3.4 Mbps on this 4 Mbps link), as the spec asks. That left about one short stall per run. Jellyfin's web client keeps a margin by using about 70% of the measured speed; whether to do the same is an open decision (reviewer finding #4).

Limits of this proof

  • The speed test measured 360 Mbps because host and VM share a fast virtual bridge; the measurement is capped at Maximum (360 Mbps). A slow-link test was not run. The bitrate limit itself is proven with a fixed 100 kbps cap.
  • The HDR10 file is synthetic (x265 test pattern with HDR10 metadata), which Jellyfin classifies as VideoRangeType=HDR10. No real Dolby Vision file was tested. DV uses the same VideoRangeType condition.
  • Audio track choice is not carried over a quality restart. A transcode carries the server's default audio track.
